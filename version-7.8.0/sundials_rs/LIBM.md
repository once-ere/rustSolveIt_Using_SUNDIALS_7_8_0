# LIBM.md — the pure-Rust elementary functions

`crates/sundials_core/src/sundials_libm.rs` implements every elementary
function this port evaluates, in safe Rust with no external crates and no
FFI. Nothing in `crates/` calls the host C library for arithmetic any more.

That is the single change this repository makes to the crate tree it
inherits, and it exists to remove one specific failure mode: on the sibling
`SUNDIALS_7_8_Rust_port_for_Linux`, three ARKODE variants stop reproducing
on Arch Linux, not because of anything in the port but because glibc 2.44
changed `sinh`, `cosh` and `acosh`. A numerical library whose printed
output depends on the patch level of the C library it happens to link
against is not reproducible; this one does not.

---

## 1. What is implemented

Thirteen functions. Twelve were requested; `exp` is the thirteenth, because
`expm1`, `sinh`, `cosh` and `pow` are all built on it and because it was
the single largest remaining host-libm call site in the tree (65 of them).

| function | algorithm | provenance |
|---|---|---|
| `exp` | ARM optimized-routines, 128-entry table, degree-5 polynomial | musl `src/math/exp.c` + `exp_data.c` — MIT, © 2018 Arm Limited |
| `log` | ARM optimized-routines, 128-entry table, degree-6 polynomial | musl `src/math/log.c` + `log_data.c` — MIT, © 2018 Arm Limited |
| `pow` | ARM optimized-routines `pow` | already present in `sundials_math.rs`; MIT, © 2018 Arm Limited |
| `expm1` | double-double Taylor series (small `x`) / `exp_dd(x) − 1` | written here |
| `log1p` | `log_dd` of the exactly-formed double-double `1 + x` | written here |
| `sin`, `cos` | exact Payne–Hanek reduction on the bits of 2/π, then a 15-term double-double Taylor kernel | written here |
| `atan` | 17-point table reduction to \|t\| ≤ 1/32, then a 12-term double-double series | written here |
| `asin`, `acos` | reduced to `atan` in double-double, with the branch chosen to avoid cancellation at \|x\| → 1 | written here |
| `sinh`, `cosh` | `e^x = m·2^k` kept unscaled, so the result is exact up to the overflow threshold | written here |
| `acosh` | `log_dd(x + √(x²−1))`, with a `log1p`-shaped branch near `x = 1` | written here |

`sqrt`, `mul_add`, `abs`, `ceil`, `floor`, `round`, `trunc` and `copysign`
are still `f64` inherent methods. IEEE-754 specifies all of them exactly;
they are identical on every target and are not part of the problem.

### The double-double core

The routines written here carry intermediate results as an unevaluated sum
`hi + lo` with `|lo| ≤ ½ ulp(hi)` — about 106 significant bits — using the
classical Dekker/Knuth/Bailey algorithms. `two_prod` uses `f64::mul_add`,
which Rust guarantees is a single fused multiply-add, so the product error
term is exact. Results are accurate to roughly 2⁻¹⁰⁰ before the single
final rounding, which is why they come out correctly rounded.

### Where the constants come from

Every table is generated by
[`tools/gen_libm_constants.py`](tools/gen_libm_constants.py), which uses
only Python's standard-library `decimal` at 120 digits. You can regenerate
and diff:

```bash
python3 tools/gen_libm_constants.py > /tmp/regenerated.rs
```

The tables are π/2 (triple-double), π, π/4, ln 2, `1/(2n+1)!`, `1/(2n)!`,
`1/(2n+1)`, `1/n!`, `atan(k/16)` for k = 0…16, `log(1 + j/64)` for
j = 0…64, and 1536 bits of 2/π for the Payne–Hanek reduction. The ARM
`exp`/`log` tables are transcribed mechanically from the musl sources, not
by hand.

## 2. How accurate they are — measured, not claimed

```bash
tools/libm_differential.sh 1000000
```

builds [`tools/libm_oracle.c`](tools/libm_oracle.c) with the host compiler
and, for each sampled input, records three things: what the **host glibc**
returned, what the correctly rounded binary64 of the **113-bit
`__float128`** value is, and how far that 113-bit value sits from the
rounding boundary. The Rust side then recovers a real-valued ulp error for
both implementations. The reference is roughly 2⁻⁶⁰ ulp better than either
candidate, so it decides every case.

**Result on Ubuntu 26.04, glibc 2.43, gcc 15.2.0, rustc 1.96.1 —
1,000,000 samples per (function, corpus), 24,000,000 in total:**


### Reading the table

Two different things are being reported, and conflating them would be a
mistake.

**The agreement column** is a fact about glibc, not a quality score.
`exp`, `log` and `pow` agree with glibc 100 % of the time because they
*are* glibc's algorithm: since 2.28/2.29 glibc ships the same ARM
optimized-routines source, and on x86-64 it ifunc-dispatches to the
`-mfma -mavx2 -ffp-contract=fast` build, which is what `f64::mul_add`
reproduces. `acosh` agrees 100 % for a different reason: glibc's `acosh`
is *itself* correctly rounded on this host, and so is ours, so they cannot
disagree.

**The error columns** are the quality score, and they are unambiguous.
0.5000 ulp is correct rounding — the smallest error a binary64 result can
have. Every function written here achieves it. glibc does not: it is
0.51 ulp on the trigonometric family, 0.78–0.84 ulp on `expm1`/`log1p`,
and up to 1.78 ulp on `sinh`.

So where the two disagree, on 0.07 % to 28 % of inputs depending on the
function, **the pure-Rust answer is the correct one and glibc's is off by
one bit.**

### Why `sin`, `cos`, `atan`, `asin`, `acos` are not bit-identical to glibc

They cannot be, and the reason is licensing rather than mathematics.
glibc implements those five with the IBM Accurate Mathematical Library
(`sysdeps/ieee754/dbl-64/{s_sin,s_atan,e_asin}.c`), which is LGPL-2.1 and
cannot be copied into this BSD-3-Clause tree. No permissively licensed
bit-identical equivalent exists.

Given that, there were two options: clone the fdlibm versions musl uses,
which are ~0.55 ulp and would disagree with glibc *more* often than a
correctly rounded routine does; or compute the correctly rounded result.
The second is both more accurate and closer to glibc, so that is what is
here.

## 3. What this costs, and what it buys

The output consequence is measured in
[`differences/ATTRIBUTION.md`](differences/ATTRIBUTION.md), not estimated.
Of 179 comparable example variants, 171 are byte-for-byte identical to the
pristine C binaries; the other 8 all become identical when the port is
rebuilt `--features host-libm`, which proves the difference is this
substitution and nothing else.

Four of those eight are the ARKODE LSRK examples — the same four the
sibling repository saw break on glibc 2.44, for the same reason, because
`SUNRsinh`/`SUNRcosh`/`SUNRacosh` feed a stage-count formula at
[`crates/arkode_rs/src/arkode_lsrkstep.rs:87`](crates/arkode_rs/src/arkode_lsrkstep.rs:87).
Where that repository has to document a platform caveat, this one has a
fixed answer that will not move.

Speed: the ARM `exp`/`log`/`pow` kernels are the same code glibc runs and
cost the same. The double-double routines are several times slower than a
hardware-tuned libm — roughly 100 ns rather than 20 ns per call. For the
example suite this is not measurable against the solver work; the full
199-variant Rust sweep runs in well under a minute.

## 4. Testing

```bash
cargo test --workspace --lib            # unit tests, no oracle needed
tools/libm_differential.sh 1000000      # the table in §2
tools/pow_differential.sh all           # pow, against the native oracle
```

The unit tests in `sundials_libm.rs` cover, independently of any oracle:

* special values — signed zeros, infinities, NaN, domain errors, the
  overflow and underflow thresholds;
* identities — `sin² + cos² = 1`, `cosh² − sinh² = 1`, `asin + acos = π/2`,
  `atan(tan x) = x`, `exp = 1 + expm1`, `acosh(cosh x) = |x|`, with
  tolerances that account for the cancellation each identity introduces;
* **huge-argument reduction** — `sin` and `cos` at 1000 arguments spread
  across the whole exponent range up to 2¹⁰²³, checked for range and for
  the Pythagorean identity. A Cody–Waite reduction fails this; the exact
  Payne–Hanek one does not.

The differential tests assert, per function, either bit-identity with the
host libm (for `exp` and `log`, where the algorithm is provably the same
upstream source, so anything else is a translation defect) or correct
rounding (for everything else). Neither assertion is a hand-tuned
tolerance. If no oracle has been built the differential tests print
"not run" and pass, so `cargo test` stays green on a machine without a C
compiler.
